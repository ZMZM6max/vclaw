### L5 层当前可运行链路

```
ToolsCapabilities.execute(action_name, params)
  → ToolRegistry.get() 查找工具
  → ParameterValidator.validate() 参数校验（含保真校验）
  → PermissionManager.check_permission() 权限检查
  → ToolExecutor._run_pre_checks() 前置检查（沙盒路径、文件存在性）
```

## 一、L5 代码对 L6 的实际接口需求

### 1.1 实际调用链路（基于 `ToolExecutor._execute_in_l6()`）

L5 XML 规范（`ToolExecutor.xml`）描述的 L6 调用链为：
```
L5.ToolExecutor
  → L6.SandboxManager.create()
  → L6.ResourceLimiter.set()
  → L6.SecurityEnforcer.validate()
  → L6.CodeExecutor.run() / L6.DockerController.exec_in_container()
  → L6.SandboxManager.destroy()
```

**实际代码中的调用链路**（`src/l5/tool_executor.py:264-303`）：
```python
if tool.name == "python_repl":
    l6_result = self._runtime.run_code("python", code, timeout=timeout)
elif tool.name == "terminal":
    l6_result = self._runtime.run_command(command, timeout=timeout)
elif tool.name == "javascript":
    l6_result = self._runtime.run_code("javascript", code, timeout=timeout)
```

即：**L5 代码仅依赖 `RuntimeInterface` 的两个方法**，所有 L6 内部分层由 `RuntimeEnvironment` 自行编排。

### 1.2 L5 → L6 数据映射（基于 `ToolExecutor._convert_l6_result()`）

| L6 `ExecutionResult` 字段 | L5 `L5ExecutionResult` 映射 | 说明 |
|--------------------------|----------------------------|------|
| `exit_code` | `metadata.exit_code` | 0 为 success，非 0 为 error |
| `stdout` | `result` | 成功时直接作为结果内容 |
| `stderr` | `result`（error 时） | 失败时优先展示 stderr |
| `execution_time` | `execution_time` | 若 L6 返回有效值则优先采用，否则用 L5 自行计时 |
| `resource_usage` | `metadata.resource_usage` | 目前为占位值 `{"memory_peak_mb": 0.0, "cpu_time_ms": 0.0}` |

### 1.3 L6 需提供的最小接口

L5 层目前仅需 L6 实现以下接口即可运行：

```python
class RuntimeInterface:
    def run_code(self, language: str, code: str, timeout: int = 30) -> ExecutionResult: ...
    def run_command(self, command: str, timeout: int = 30) -> ExecutionResult: ...

class ExecutionResult:
    exit_code: int
    stdout: str
    stderr: str
    execution_time: float
    resource_usage: dict
```

> **影响**：L6 的 `SandboxManager`、`ResourceLimiter`、`CodeExecutor` 三个组件从 L5 视角属于内部实现细节，不影响 L5 对接。L6 计划应优先保证 `RuntimeEnvironment` 的稳定性，而非强制将上述三个组件暴露给 L5。

## 八、架构问题与风险

| 编号 | 问题 | 影响 | 建议方案 |
|------|------|------|----------|
| ARCH-001 | `SandboxManager` 与 `DockerSandbox` 功能高度重叠 | 二者都直接操作 `DockerController`，代码重复，维护成本高 | 明确分层：`SandboxManager` 作为抽象协调层，`DockerSandbox` 作为其默认实现；合并重复逻辑 |
| ARCH-002 | `CodeExecutor` 为死代码 | 全项目无人导入，造成"已实现却不可用"的假象 | 直接移除 `code_executor.py`，或将其逻辑合并入 `RuntimeEnvironment` |
| ARCH-003 | `ResourceLimiter` 仅作为常量库使用 | 动态资源限制能力（`set()` / `check()`）未在 RuntimeEnvironment 中使用 | 若 DockerSandbox 已用 Docker API 直接限制资源，可删除 `ResourceLimiter`；若需统一配额管理，则接入 RuntimeEnvironment |
| ARCH-004 | `ExecutionLogger` 无持久化 | 审计日志进程重启丢失，不符合生产环境要求 | 实现文件追加或结构化日志 |
| ARCH-005 | `ExecutionResult.resource_usage` 为占位值 | 返回永远为 0.0，无法用于资源审计和计费 | 接入 Docker stats API 或 cgroups 读取真实用量 |
| ARCH-006 | L5 Spec 与 L5 代码在 L6 调用链上不一致 | Spec 要求显式调用 SandboxManager/ResourceLimiter/CodeExecutor，代码直接调用 `runtime` | 两种选择：a) 修改 L5 代码以匹配 Spec；b) 修改 Spec 以匹配代码。鉴于 L5 代码已稳定运行，建议 **修改 Spec**（已在 `L5_ToolsCapabilities.xml` 中简化描述） |

## 十二、如何维护本文档

1. **每次修改 L5 代码后**：检查【二】L5 组件实现状态表是否需要变更；若新增代码超出 XML Spec，同步补充 Spec。
2. **每次修改 L6 代码后**：检查【三】L6 组件实现状态表是否需要变更（如 ❌ → ⚠️ → ✅）。
3. **每次新增 L5/L6 测试后**：更新【四】和【五】中的验证状态，标记已通过的测试用例 ID。
4. **每次新增功能后**：
   - 若功能已完成，移至【四】已完成的 L6 功能
   - 若功能从"未来"调整为"当前计划"，更新【六】计划实现的 L6 功能
5. **定期对照 XML**：每月（或每轮迭代）重新阅读 `src/l5/l5 specs/` 和 `src/l6/l6 specs/` 下的 XML，确保本文档无遗漏、无过期。
